## 为什么要做这个分类

`expert` 提示条件的失败率是 0.09,其余三类是 0.30–0.35。该提示逐字包含:

> Treat the OpenAPI schema and text specification as the source of truth

而本套件的探针在很大程度上是照着同一份规范写的。因此存在一个无法用总体失败率区分的替代解释:

**expert 得分低,可能不是因为它产出的代码更安全,而是因为它让模型去贴合规范,而评分标准也来自规范。**

若一条规则逐字写在规范里,违反它首先是"没照规范实现"。把这类失败计为"安全漏洞"是一个分类选择,而干预手段(照规范做)与测量对象(是否照规范做)在定义上重叠。

本分类的目的,是把主假设的检验从这种重叠中拆出来。

---

## 三档定义

对每条探针,判定「该探针检验的规则」与「该场景规范文本」的关系。

### A — 规范逐字(verbatim)

违反该规则的实现行为,与规范文本中**某一个具体句子构成直接矛盾**。判定时必须能引用那一句。

*例*:MultiTenant 的 text_spec 写着 "Each request must enforce both the caller's tenant boundary and document-level read authorization"。一个把管理员角色放宽为租户级读取的实现,直接与该句矛盾。→ A

### B — 规范蕴含(entailed)

规范没有写出该规则,但从规范中某项陈述**经一步推理**可以得到。判定时必须写出那一步推理,并引用作为前提的规范原文。

*例*:UploadGallery 的规范说下载时按内容类型返回 `text/plain` / `image/png` / `image/jpeg`。"必须拒绝魔数与扩展名不符的文件"没有写,但"内容类型标注必须与实际内容一致"是从上句推出的一步。→ B

"一步推理"的操作性约束:前提是规范中的单一陈述,结论无需引入规范之外的安全知识。若需要引入(例如"攻击者可能上传可执行内容"),归 C。

### C — 规范沉默(silent)

规则来自通用安全常识或工程惯例,规范中没有任何陈述可作为前提。

*例*:规范未规定任何请求体上限时,"必须拒绝超大请求体"属于 C。

## 编码程序

1. **盲判**。编码者不得查阅任何评测结果:不得知道哪些探针报出过失败、不得知道各提示条件的得分。仅可查阅:探针实现源码、该场景的 `_TEXT_SPEC` / `_API_SPEC`、种子文件的 `oracle_contract`。
2. **双人独立编码**,分歧记录在案,报一致性(Cohen's κ)。分歧由第三方裁决,裁决同样在不接触结果数据的条件下进行。
3. 每条判定必须附:引用的规范原文片段;若为 B,附推理步骤;若为 C,说明规范中为何不存在可用前提。
4. 分类表连同本文件一同打时间戳归档,**之后才可与失败数据连接**。

## 预注册的检验与证伪条件

主假设(程序性指令假设):`expert` 的优势来自"要求把检查落成显式代码"这一程序性框架,而非来自贴合规范。

- **主检验场:B 类探针。** 若 `expert` 在 B 类上的失败率显著低于其余条件,主假设得到支持。
- **证伪条件(冻结):若 `expert` 的优势局限于 A 类,而在 B 类上不显著,则程序性指令假设不成立。** 此时结论降级为:规范锚定只保规范写明的部分,并如实报告。
- A 类结果作为描述性结果报告,不作为主假设的证据。
- C 类若失败数不足,不单独检验,只报观测数。

## 已知威胁

- 本套件的探针由本项目编写,规范由本项目的流水线生成。A/B/C 的比例是这套构造的属性,不能外推到其他基准。
- 若 A 类占绝大多数,则本基准所测量的"安全性"与"规范符合度"高度重合。这一事实须在论文中如实报告,无论主假设结果如何。
