## 一、为什么需要这份说明

冻结协议第五节把模型可见面切成两类,并给出三条规则:

1. `api_spec` 中 **description 字段内的义务性散文** —— 与 `text_spec` 同等处理,一并摘除
2. **结构性元素(状态码枚举、schema 约束、必填字段)** —— 保留,视为功能契约(等同 A-con)
3. **依据仅存在于结构性元素的 A-sec 探针** —— 无法去锚,排除出第 (i) 层并落表

手术执行时发现:OpenAPI 操作级的 **`security:` 要求对象**

```yaml
paths:
  /notes:
    get:
      security:
        - bearerAuth: []
```

**不属于上述任何一类**。它不是 description 里的散文(规则 1 不覆盖),也不在规则 2 列举的三类之内——规则 2 的三类(状态码枚举、schema 约束、必填字段)全部是**数据形状契约**,而 `security:` 声明的是**访问规则**。

协议冻结时未预见此元素。本说明补上这个空隙。

## 二、裁定

**`security:` 要求对象按义务处理,与 `text_spec` 中的认证义务句一并摘除。**

保留:
- `components.securitySchemes` 的**定义**(令牌格式、scheme 类型)——它描述凭据长什么样,是数据形状
- `401` / `403` **响应状态码枚举**——协议规则 2 明确保留

摘除:
- 各操作下的 `security: - <scheme>: []` **要求对象**

## 三、理由

协议第五节自己写明了可见面界定的目的:

> **义务若在 api_spec 中存活,致盲即不完全,结果一可能是漂白假象。**

`security: - bearerAuth: []` 是"本端点必须要求认证"的机器可读表述。而认证类探针检验的恰恰就是这条义务。若保留它,则:

- 文字规范里摘掉了"此操作需要有效的 bearer 令牌"
- OpenAPI 里仍然明写着该端点要求 bearer 认证

模型据后者仍会实现认证。这批探针**只去锚一半**,一旦出现"结果一:复活",无法排除它来自残留锚定——正是协议警告的漂白假象。

规则 2 保留结构性元素的**理由**是它们是功能契约:摘掉数据形状会改变 API 契约本身,使功能测试与安全结局混淆。`security:` 不具备这个属性——摘掉它不改变任何请求/响应的形状,不影响任何功能测试的断言,只是不再言明访问须受限。这与协议第五节的正例(MultiTenant:摘除"每个请求必须强制租户边界与文档级读授权",保留文档归属租户等领域事实)形态完全一致。

## 四、自由度申报

**本裁定放宽了摘除范围。** 按字面严格读,`security:` 可被归入"结构性元素"而保留。选择摘除,是在协议冻结之后作出的、方向上使干预更强的解释。

如实申报三点:

1. **作出时间**:2026-08-17,在任何致盲版规范生成之前、任何样本产出之前。本文件的哈希与 commit 时间戳构成证据。
2. **作出依据**:协议第五节明文的立法意图(避免致盲不完全导致漂白假象),非数据驱动。作出时无任何本实验的生成结果存在。
3. **影响范围**:约 15–20 条认证类探针的归层。手术表中每条受影响的记录带 `PR-1` 标记,可逐条复核。

## 五、须写进论文限制

成稿时在限制一节列出:

> 模型可见面的界定中,OpenAPI 操作级 `security:` 要求对象按安全义务处理并予摘除。该元素未被冻结协议的三条可见面规则覆盖;此裁定在任何数据产出前作出并单独归档(解释说明一),但它确系冻结后的解释,方向上使干预更强。严格按字面执行(保留 `security:`)将使认证类探针只去锚一半。

## 六、未采纳的备选

- **备选 A(严格字面)**:保留 `security:`。程序上零自由度质疑,但认证类探针致盲不完全,须在结论中声明该批探针的"复活"不可解释。
- **备选 C(双跑)**:主分析按 A、稳健性检验按 B,两个结果都报。最严谨,但生成量与预算翻倍。

采纳 B,并以本说明与 §10 限制条目承担其代价。
