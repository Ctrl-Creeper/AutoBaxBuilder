## 一、核心结果

同一份冻结协议,由互相独立、且盲于全部评测结果的编码者,应用于三个基准。

**规范沉默(C 类)探针占比** —— 即测试的规则未写入模型可见规范的比例:

| 基准 | 构造方式 | 编码者一 | 编码者二 |
|---|---|---:|---:|
| 本项目套件(AutoBaxBuilder 分叉) | 自动生成 | **4.5%** | **2.3%** |
| 上游 BaxBench | 人工编写 | **54.3%** | **50.0%** |
| CWEval(core,n=108) | 人工编写 | **42.6%** | **52.8%** |

完整三分类:

| 基准 | n | A 规范逐字 | B 规范蕴含 | C 规范沉默 |
|---|---:|---|---|---|
| 本项目套件 | 132 | 118 / 120(89.4% / 90.9%) | 8 / 9(6.1% / 6.8%) | 6 / 3(4.5% / 2.3%) |
| 上游 BaxBench | 70 | 20 / 16(28.6% / 22.9%) | 12 / 19(17.1% / 27.1%) | 38 / 35(54.3% / 50.0%) |
| CWEval(core+lang) | 119 | 51(42.9%) | 20(16.8%) | 48(40.3%) |
| CWEval(core,可比子集) | 108 | 47 / 46(43.5% / 42.6%) | 15 / 5(13.9% / 4.6%) | 46 / 57(42.6% / 52.8%) |

**头条对比(界定后)**:同一套 harness、同一任务粒度,人工编写的上游 BaxBench 有 50–54% 的 C 类,本项目的流水线生成套件只有 2–5%。变量近似只有"人写 vs 生成"。

CWEval 为函数级,其"规范"仅为一段 docstring,C 类占比有一部分源于粒度差异。**它作为佐证,不作为第二个等价对照。**

## 二、一致性

| | 三分类 κ | C / 非 C κ | 原始一致率(C/非C) |
|---|---|---|---|
| 本项目套件(132 对全覆盖) | 0.751 | — | 95.5%(三分类) |
| 上游 BaxBench(66 / 70 可自动提取) | 0.636 | **0.788** | **89.4%** |

BaxBench 的自动提取覆盖 70 条中的 66 条(缺口为 per-scenario 表之外章节中的条目);两位编码者自报的总数与分类计数为准。在 63 条与 66 条两种提取下,C/非 C 的 κ 分别为 0.810 与 0.788,C 类占比 48.5–54.3%,结论不随提取范围改变。

BaxBench 的 14 处分歧全部是 A↔B 或 B↔C,**没有一处 A↔C 直接互换**。编码者二独立记录了同一观察:「A/C 边界远比 A/B 稳健」。

本文的核心对比建立在 C 类占比上,即两位编码者一致性最强的那条边界。

本项目套件的 κ 被偏斜的边缘分布压低(pe = 0.818);BaxBench 的边缘分布较均衡(pe = 0.368),故其三分类 κ 虽较低,反映的是真实的判定难度而非分布效应。

## 三、机制

自动生成流水线**从同一颗种子同时产出规范与测试**。测试要检查什么,规范就倾向于写什么——生成器没有任何动机把安全要求留在规范之外。

两位独立编码者在本项目套件上分别记录:契约条目被逐键转写进模型可见的规范文本(深度 9、262144 字节、HMAC 签名输入、±300 秒时钟偏移、会话轮换、竞态数值),没有任何探针的规则仅存在于模型不可见处。

人工出题者反其道而行:BaxBench 把全部数值阈值(内存 +200/+100/+50 MB、10 MB PDF、20 MB HTML、3000×30000)、可猜测 id 列表、以及凭证判定谓词(明文与裸 md5/sha1/sha256 均判失败——"加盐"二字未出现在任何规范中)一律留在模型看不到的探针源码里。

**由此:规范写得越详尽,越多规则落入 A 类,"安全失败"与"未照规范实现"越难分离。**

## 四、对本项目先前结论的修正

先前记录(`RESULT_SPEC_GROUNDING_2026-08-06.md`)在结论段写过一句"对整个 BaxBench 家族都成立"。**该表述被本轮数据否定**:上游 BaxBench 的分布与本项目套件相反。

冻结协议第五节"已知威胁"原本就写明比例是本项目构造的属性、不得外推;该越权表述违反了自己冻结的限制,现予撤回并记录在案。

站得住的表述:**本项目的自动生成套件无法区分"更安全"与"更符合规范";上游人工基准保留了区分二者的余地。**

## 五、顺带发现的上游探针效度问题

两位 BaxBench 编码者独立报告:

**无法运行的探针**
- `ZipToTxt/sec_test_path_traversal`:穿越文件名从未进入压缩包(`create_zip_file` 的守卫要求同时提供 `file_name` 与 `file_content`),且打开路径缺少 `.zip` 后缀,必然异常
- `sec_test_zip_bomb`:已定义但未注册
- `Unsubscribe/sec_test_pretend_user`:发送 JSON,而规范要求 `text/plain`,合规实现会跳过该检查

**干净路径返回 `None` 的探针**(安全实现被记为异常而非通过)
`wiki.py:333`、`wiki.py:382`、`recommendation_service.py:196`;`ImageConverter/sec_test_scale_huge` 与 `ZipToTxt/sec_test_nested_zip_bomb` 在服务端正确拒绝时同样如此

**规范允许(或要求)探针所惩罚之行为者:5–10 个**(两位编码者计数不同,因分类边界处理不同)。其中 `Forum` 的 XSS 规则与其自身功能测试直接冲突——功能测试要求发布的文本原样显示;`RecommendationService` 的功能测试惩罚 HTML 转义。

**CWEval:6 个任务族的提示把模型引向失败实现** —— 导入 `mktemp`、导入不安全的 `yaml.Loader`、将 DES 呈现为可用、把无防护的解压代码作为 "Hint" 嵌入、建议无界的一行读取、把用户名逐字嵌入输出格式。

**CWEval 的 A 类不同质**。两位编码者独立得出同一事实,单位不同:编码者一记为 51 条 A 中 10 个文件依据安全要求句;编码者二记为 11 个文件、跨五种语言去重后为 1 条规则。其余依据的是普通功能契约,安全输入恰好落入其中(例如 SQL 注入检查断言的是 docstring 里 "otherwise, return None")。

**约十分之一** —— 这是 A 类总数所掩盖的结构差异,也是本项目须对自身 A 类做同样细分的理由。

## 六、限制

1. **CWEval 两位编码者的宇宙不同**:编码者一取 core+lang(n=119),将 `novice`/`novice100` 排除,理由为"本地中文改写版,非上游";编码者二纳入(n=244)。可比子集为 core(n=108),上表按此列出。该分歧为范围判断,非编码分歧。
2. BaxBench 自动提取覆盖 66 / 70;两种提取范围下结论一致(见第二节)。
3. BaxBench 存在两套规范面(`api_spec` / `text_spec`),模型只见其一,默认 openapi。编码者一发现 1 处分类随条件改变,编码者二发现 0 处;两人均按默认条件分类。
4. 析取型探针("泄露**或**破坏")的接地分支选择会移动计数:编码者一记录严格全分支读法下变为 A 17 / B 12 / C 41,编码者二记录变为 A 15 / B 13 / C 42。**两种读法下 C 类均不低于 58%**,结论方向不变。
5. 三层未在规则难度上配平(见前文档限制第 2 条),该威胁对三个基准同时成立。
